## Question

[Ticket 058](058-topic-sharing-details.md) ตัดสินให้ผู้รับแบบจำกัดอีเมลต้องล็อกอินด้วยบัญชีที่อีเมลตรง และตัดสินให้ **เพิ่มการยืนยันอีเมลตอนสมัคร** (เพราะตอนนี้ใครสมัครด้วยอีเมลของใครก็ได้) ต้องตัดสิน: (1) ต้องยืนยันก่อนล็อกอินได้ หรือล็อกอินได้แต่ใช้การแชร์แบบจำกัดอีเมลไม่ได้จนกว่าจะยืนยัน (2) ลิงก์ยืนยันหมดอายุเมื่อไร และส่งซ้ำได้อย่างไร (3) บัญชีเดิมที่มีอยู่ (ข้อมูลเดิมลบได้ตาม ticket 053) (4) การเปลี่ยนอีเมลภายหลัง (5) ใช้ตัวเลือกการส่งอีเมลแบบไหน (หลังได้ข้อเท็จจริงจาก [ticket 062](062-research-email-sending-options.md)) (6) ต้องยกเลิก/แก้ ADR-0011 หรือไม่ (7) กระทบหน้าสมัคร/ล็อกอินที่มีอยู่อย่างไร

## Resolution

เจ้าของโปรเจกต์ตัดสิน (2026-10-06) การยืนยันอีเมลตอนสมัคร (ต่อจาก [ticket 058](058-topic-sharing-details.md) ที่ตัดสินให้แชร์แบบจำกัดอีเมลต้องล็อกอินด้วยบัญชีที่อีเมลตรง):

- **ต้องยืนยันก่อนใช้แอป**: สมัครเสร็จ **ยังไม่ล็อกอิน** (ต่างจากปัจจุบันที่ล็อกอินให้ทันที) ต้องกดลิงก์ในอีเมลก่อนถึงจะล็อกอินและใช้แอปได้ — คำตอบของเจ้าของโปรเจกต์ ต่างจากที่ผู้บันทึกแนะนำ (ให้ใช้ได้ทันที ยืนยันทีหลังเฉพาะการดูลิงก์แชร์); ผลที่รับทราบ: ถ้าอีเมลตกสแปม/ส่งไม่สำเร็จ ผู้ใช้ใช้แอปไม่ได้จนกว่าจะส่งซ้ำสำเร็จ; ผลต่อเนื่อง: บัญชีที่ล็อกอินได้ทุกบัญชีเป็นบัญชีที่ยืนยันแล้ว จึงไม่ต้องมีสถานะ "ยังไม่ยืนยัน" ตอนเปิดลิงก์แชร์
- **ลิงก์ยืนยัน**: หมดอายุ **24 ชั่วโมง**
- **ส่งซ้ำ**: ผู้ใช้กด "ส่งอีเมลยืนยันอีกครั้ง" ได้ พักระหว่างครั้ง **60 วินาที** และไม่เกิน **5 ครั้งต่อชั่วโมงต่อบัญชี**
- **กันการใช้ในทางที่ผิด**: จำกัดจำนวนการสมัครและการขอส่งซ้ำ **ต่อ IP ต่อชั่วโมง** ด้วย (ตัวเลขตั้งต้น ปรับได้ — รายละเอียดการนับเป็นขั้นออกแบบ)
- **บัญชีเดิม**: ลบพร้อมข้อมูลเดิม (ตาม [ticket 053](053-topic-note-merge-consequences.md)) ถ้าจำเป็นต้องเก็บไว้ให้ตั้งเป็น "ยังไม่ยืนยัน"
- **การเปลี่ยนอีเมล**: **ไม่เพิ่มใน v2** (ถ้าเพิ่มภายหลังต้องยืนยันอีเมลใหม่ เป็นเรื่องใหม่)
- **วิธีส่ง**: **บริการส่งอีเมลภายนอก** (ผ่าน API หรือ SMTP ของบริการ) — ยังไม่เลือกผู้ให้บริการ (นอก scope ของ map นี้; ข้อเท็จจริงเปรียบเทียบใน [ticket 062](062-research-email-sending-options.md))
- **ส่งอีเมลไม่สำเร็จ**: การสมัครยังสำเร็จ (บัญชีถูกสร้างแบบยังไม่ยืนยัน) ผู้ใช้เห็นข้อความ "ส่งอีเมลยืนยันไม่สำเร็จ กดส่งอีกครั้งได้" และมีปุ่มส่งซ้ำ; ความล้มเหลวนี้ **ถูกบันทึกลง Error Log** — **ขยายรายการของ [ticket 055](055-error-logging-details.md)** จาก "เรียก AI ไม่สำเร็จ" เป็น "เรียกบริการภายนอกไม่สำเร็จ" (รวมการส่งอีเมล)

**คำตอบเพิ่มเติม (2026-10-06 หลังปิด ticket)**: (1) **ยังไม่มีโดเมน**ที่แก้ DNS ได้สำหรับที่อยู่ผู้ส่ง — เป็นเงื่อนไขที่ต้องทำก่อนส่งอีเมลจริง (research 062: ไม่มีโดเมนที่แก้ DNS ได้ อีเมลมีโอกาสตกสแปม และผู้ให้บริการส่วนใหญ่ต้อง verify โดเมนก่อนส่ง) จดเป็นงานเตรียมการก่อน build ส่วนส่งจริง ไม่ใช่การตัดสินใจ (2) ตอน dev ในเครื่อง **ใช้ตัวรับอีเมลจำลองใน docker-compose** (เช่น Mailpit/smtp4dev ที่ research พบว่ายังพัฒนาอยู่ ยังไม่เลือกตัวใดตัวหนึ่ง) เพื่อไม่ต้องส่งจริง — เปลี่ยนจาก "docker-compose รันเฉพาะ PostgreSQL" ใน ARCHITECTURE.md หัวข้อ Local development ต้องแก้ในขั้นเอกสารปิดท้าย

**ข้อกำหนดที่ส่งต่อขั้นออกแบบ (ผลจากการเลือก "ยืนยันก่อนใช้แอป")**: เมื่อบัญชียังล็อกอินไม่ได้ ปุ่ม "ส่งซ้ำ" ต้องทำงานได้โดยไม่ล็อกอิน (ส่งโดยระบุอีเมล) จึงต้องตอบข้อความเดียวกันเสมอไม่ว่าอีเมลนั้นมีในระบบหรือไม่ (กันการเดาว่าอีเมลใดสมัครไว้) และต้องใช้การจำกัดต่อ IP ข้างบนกันการรัวส่ง; ผู้ที่ล็อกอินด้วยรหัสผ่านถูกต้องแต่บัญชียังไม่ยืนยันควรเห็นข้อความที่บอกให้ยืนยันอีเมล (ต่างจากรหัสผ่านผิด)

**ผลต่อเอกสาร (ขั้นเอกสารปิดท้าย ยังไม่แก้ไฟล์)**: ADR-0011 (Identity) ต้องมี ADR ใหม่หรือแก้ไข — `User` มีสถานะยืนยันอีเมล และมี token ยืนยันที่สร้างเอง (ไม่ใช้ `UserManager`); ARCHITECTURE.md หัวข้อ Auth (ขั้นตอนสมัครใหม่ไม่ล็อกอินให้ทันที, ส่งอีเมลผ่านบริการภายนอก) และ Local development (ถ้าเพิ่มตัวรับอีเมลจำลอง); ticket 055 resolution ขยายรายการ

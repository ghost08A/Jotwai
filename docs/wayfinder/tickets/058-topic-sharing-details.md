## Question

(`requirements-v2.md` §2.2) Behavior หลักสรุปแล้ว (ลิงก์ read-only ของ subtree, Public หรือจำกัด Email, วันหมดอายุ) ที่เหลือต้องตัดสิน: การยืนยันตัวตนของผู้รับแบบจำกัด Email, การเพิกถอน/แก้ไข Link, หนึ่ง Topic มีหลาย Link ได้ไหม, การเปลี่ยนโครงสร้าง subtree หลังแชร์ (ย้าย/เพิ่ม/ลบ Subtopic), สิ่งที่ผู้รับมองเห็น (Category, Description, ไฟล์แนบ), และข้อมูลอะไรที่ไม่ควรโผล่ให้ผู้รับ

## Progress (ตอบแล้วบางส่วน — ticket ยังเปิดอยู่)

เจ้าของโปรเจกต์ตอบรอบ 1 (2026-10-06):

- **ผู้รับแบบจำกัดอีเมล**: ต้อง **ล็อกอินเข้า Jotwai ด้วยบัญชีที่อีเมลตรงกับรายการ** (ไม่สร้างระบบส่งอีเมล) ข้อเท็จจริงที่ต้องรับทราบ: ตอนนี้การสมัครไม่ยืนยันอีเมล (ถามต่อ)
- **เปลี่ยนแปลงลิงก์**: ปิดลิงก์ทันที, เปลี่ยนรูปแบบ, เพิ่ม/ลบอีเมล, แก้วันหมดอายุ ได้ทั้งหมด; วันหมดอายุเป็นตัวเลือก (ไม่ตั้ง = ไม่หมดอายุ); ลิงก์หมดอายุแสดงหน้า "ลิงก์หมดอายุ" และเจ้าของต่ออายุได้
- **จำนวนลิงก์ต่อ Note**: **หลายลิงก์ได้** ลิงก์ละการตั้งค่า (รูปแบบ อีเมล วันหมดอายุ) ยกเลิกแยกกันได้ (ผู้บันทึกถือว่าครอบคลุมเรื่องลิงก์แม่/ลูกทำงานอิสระต่อกัน)
- **โครงสร้างหลังแชร์**: การแชร์คือ "ดูทุกอย่างใต้ Note แม่ ณ ตอนเปิดดู" ไม่ใช่ภาพถ่าย — เพิ่มลูกใหม่ผู้รับเห็นทันที / ย้ายลูกออกแล้วหาย / ย้ายเข้ามาแล้วเห็น / ลูกที่ถูกลบหายและกลับมาเมื่อกู้ / ลบแม่ที่แชร์ = ลิงก์ใช้ไม่ได้ และ**กลับมาใช้ได้เมื่อกู้แม่คืน** / ย้ายแม่ไปใต้ Note อื่น ลิงก์ยังใช้ได้ ผู้รับไม่เห็นว่าอยู่ใต้ใคร
- **ผู้รับเห็น**: ชื่อและเนื้อหาแบบอ่านอย่างเดียว, โครงสร้างต้นไม้ของลูก, **Category**, **Description**, วันที่สร้าง/แก้ไขล่าสุด — **ไม่เห็น**: ค้นหาภายในที่แชร์, ชื่อ/อีเมลเจ้าของ, ชื่อ Note ที่อยู่เหนือแม่ที่แชร์ (ไฟล์แนบ ถามใน ticket 059)
- **ติดตามผู้เปิดดู**: ไม่เก็บอะไรเลย

## Resolution

เจ้าของโปรเจกต์ตัดสินครบ (2026-10-06) รายละเอียด Note Sharing (เดิมเรียก Topic Sharing — ตาม ticket 053 เลิกใช้คำว่า Topic) โดยใช้พฤติกรรมหลักจาก `requirements-v2.md` §2.2 (ลิงก์ read-only ของ subtree, Public หรือจำกัดอีเมล, วันหมดอายุ):

- **ผู้รับแบบ Public**: เปิดผ่านลิงก์ได้โดยไม่ต้องมีบัญชี
- **ผู้รับแบบจำกัดอีเมล**: ต้อง **ล็อกอินเข้า Jotwai ด้วยบัญชีที่อีเมลตรงกับรายการ** (ไม่มีระบบส่งรหัส/ลิงก์ยืนยันเฉพาะการแชร์) และ **เพิ่มการยืนยันอีเมลตอนสมัคร** เพื่อให้พิสูจน์ได้ว่าเจ้าของอีเมลเป็นผู้ล็อกอินจริง (ตอนนี้ใครสมัครด้วยอีเมลของใครก็ได้ — เป็นช่องโหว่ที่ทำให้การจำกัดอีเมลไม่มีความหมาย) — รายละเอียดการยืนยันอีเมลแยกเป็น [ticket 061](061-email-verification-at-registration.md) (ต้องสร้างระบบส่งอีเมลใหม่ทั้งชุด; ข้อเท็จจริงตัวเลือกใน [ticket 062](062-research-email-sending-options.md)) การแชร์แบบจำกัดอีเมลจะไม่ปลอดภัยจนกว่า 061 ถูก build
- **จำนวนลิงก์**: Note หนึ่งอันมี **หลายลิงก์** ได้ ลิงก์ละการตั้งค่า (รูปแบบ อีเมล วันหมดอายุ) ยกเลิกแยกกันได้ ลิงก์ของ Note แม่กับลูกทำงานอิสระต่อกัน (ผู้บันทึกถือว่าครอบคลุมโดยปริยายจากการเลือกหลายลิงก์)
- **เจ้าของแก้ลิงก์ได้**: ปิดลิงก์ทันที, เปลี่ยนรูปแบบ, เพิ่ม/ลบอีเมล, แก้วันหมดอายุ (ขยาย/ย่น/เอาออก) — วันหมดอายุเป็น**ตัวเลือก** (ไม่ตั้ง = ไม่หมดอายุ)
- **ขอบเขตที่ผู้รับเห็น = "ทุกอย่างใต้ Note แม่ ณ ตอนเปิดดู" (ไม่ใช่ภาพถ่าย)**: เพิ่มลูกใหม่ผู้รับเห็นทันที; ย้ายลูกออกแล้วหาย; ย้ายเข้ามาแล้วเห็น; ลูกที่ถูกลบหายและกลับมาเมื่อกู้; ลบ Note แม่ที่แชร์ = ลิงก์ใช้ไม่ได้ และ **กลับมาใช้ได้เมื่อกู้แม่คืน** (ไม่ถูกยกเลิกถาวร); ย้ายแม่ไปใต้ Note อื่น ลิงก์ยังใช้ได้ ผู้รับไม่เห็นว่าอยู่ใต้ใคร
- **ผู้รับเห็น**: ชื่อและเนื้อหาแบบอ่านอย่างเดียว, ต้นไม้ของ Note ลูก (กดเปิดได้), **Category**, **Description**, วันที่สร้าง/แก้ไขล่าสุด — ข้อควรรู้: Description ที่ AI สร้างจะถูกคนนอกเห็น
- **ผู้รับไม่เห็น**: การค้นหาภายใน Note ที่แชร์, ชื่อ/อีเมลของเจ้าของ, ชื่อ Note ที่อยู่เหนือ Note แม่ที่แชร์
- **ไฟล์แนบ**: ยังไม่ตัดสิน (ถามใน [ticket 059](059-attachments-architecture.md))
- **ติดตามผู้เปิดดู**: ไม่เก็บอะไรเลย
- **ข้อความเมื่อผู้รับเข้าไม่ได้**: ลิงก์ **หมดอายุ** บอกแยก (ให้ผู้รับรู้ว่าไปขอต่ออายุได้); กรณีอื่น (ลิงก์ผิด/ไม่มี/ถูกปิด, อีเมลไม่อยู่ในรายการ, Note แม่ถูกลบ) ใช้ข้อความเดียวกัน ("ลิงก์นี้ใช้ไม่ได้") ไม่บอกเหตุผล เพื่อไม่รั่วว่า Note มีอยู่จริง

**ไม่ได้ตัดสิน (ขั้นออกแบบ/ ticket อื่น)**: รูปแบบลิงก์และการสร้างรหัสที่เดาไม่ได้; การป้องกันการยิงลิงก์ซ้ำๆ (rate limit) — การแชร์เป็นจุดแรกของระบบที่เปิดให้ **คนที่ไม่ล็อกอินอ่านข้อมูลผ่าน API** (ปัจจุบันทุก endpoint นอกจากล็อกอินต้องมี token); การแสดงตัวบ่งชี้ใน UI ว่า Note ใดถูกแชร์อยู่ (กันย้าย Note เข้ามาใต้แม่ที่แชร์อยู่โดยไม่รู้ตัว); การจัดการเมื่ออีเมลของบัญชีเปลี่ยน (อยู่ใน 061)

**ผลต่อเอกสาร (ขั้นเอกสารปิดท้าย ยังไม่แก้ไฟล์)**: ARCHITECTURE.md ยกเลิก non-goal "ไม่มีการแชร์" (เฉพาะแชร์แบบอ่านอย่างเดียว) + หัวข้อ Auth (ผู้รับที่ไม่ล็อกอิน, การยืนยันอีเมล) + ต้องมี ADR (public read path, การยืนยันอีเมล); GLOSSARY เพิ่มคำ **Share / Share Link**, อัปเดตนิยาม Note (Description ถูกแสดงต่อผู้รับ)

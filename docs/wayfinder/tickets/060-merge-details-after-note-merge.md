## Question

หลังรวม Topic+Note ([ticket 053](053-topic-note-merge-consequences.md)) กฎหลักของ Merge ตัดสินแล้ว (ผู้รอดเป็น Note เดิมเสมอ, ผู้ใช้เลือกเรื่องเนื้อหา 4 แบบตอนยืนยัน) แต่ยังไม่ได้ตัดสิน: (1) Category ของ Note ที่ถูกรวม (Note ใหม่) ไปไหน — ย้ายมาติดที่ Note เดิม / ทิ้ง / ให้ผู้ใช้เลือก (2) ลูกของ Note ใหม่ที่ชื่อซ้ำกับลูกของ Note เดิมหลังย้ายมา — ซ้ำได้พร้อมคำเตือนตามกฎใหม่หรือไม่ (3) dialog ยืนยัน (กู้คืนไม่ได้) หน้าตาและข้อมูลที่ต้องโชว์ก่อนกดยืนยัน (4) Merge ใช้เงื่อนไข "ซ้ำ" แบบเดิม (เทียบชื่อ) ต่อไปได้ไหมในเมื่อชื่อซ้ำเป็นเรื่องปกติแล้ว

## Resolution

เจ้าของโปรเจกต์ตัดสินครบ (2026-10-06) รายละเอียดการรวม Note (Merge) — ต่อจากกฎหลักใน [ticket 053](053-topic-note-merge-consequences.md) (AI เสนอรวม Note ใหม่ **B** เข้ากับ Note เดิม **A**; ผู้รอดคือ A เสมอ; ชื่อ/ตำแหน่ง/ลูกของ B ย้ายมาอยู่ใต้ A; ผู้ใช้เลือกเรื่องเนื้อหา 4 แบบตอนยืนยัน: เก็บของ A อย่างเดียว / ของ B อย่างเดียว / ต่อ B ท้าย A / ต่อ A ท้าย B; ปุ่มยืนยันต้องตรวจว่าเนื้อหาไม่เปลี่ยนหลัง AI คำนวณตาม [ticket 056](056-concurrent-editing.md)):

**ของที่ผูกกับ B**
- **Category ของ B**: ย้ายไปติดที่ A (ถ้า A มีป้ายนั้นอยู่แล้วไม่ซ้ำ)
- **Description ของ B**: A ใช้ Description ของตัวเองเสมอ ถ้า A ไม่มี ใช้ของ B
- **ไฟล์แนบของ B**: ถ้าเนื้อหาของ B ถูกเก็บไว้ (เก็บของ B อย่างเดียว หรือต่อท้าย) **ย้ายความเป็นเจ้าของไฟล์** มาเป็นของ A (ไม่คัดลอก ไม่นับพื้นที่ซ้ำ); ถ้าเนื้อหาของ B ถูกทิ้ง ไฟล์ของ B ถูกเก็บกวาดตามกฎ 7 วันของ [ticket 059](059-attachments-architecture.md)
- **ลิงก์แชร์ของ B**: **ยกเลิก** ไม่โอนไปเป็นของ A (กันขอบเขตการแชร์เปลี่ยนไปโดยไม่ตั้งใจ — A อาจมีลูกที่ผู้รับไม่ควรเห็น)
- **การ์ดลิงก์จาก Note อื่นที่ชี้ไป B**: **ชี้ต่อไปที่ A อัตโนมัติ** (คำตอบของเจ้าของโปรเจกต์ ต่างจากที่ผู้บันทึกแนะนำ) — ข้อควรระวังที่ส่งต่อขั้นออกแบบ: การทำให้ลิงก์ชี้ A **ต้องไม่ไปแก้เนื้อหาของ Note อื่นแบบเงียบๆ** (ชนกับ [ticket 056](056-concurrent-editing.md) เรื่องการแก้พร้อมกัน) ควรเป็นกลไกเปลี่ยนเส้นทาง (alias/redirect) มากกว่าการเขียนทับเนื้อหา; ยังไม่ได้ตัดสินว่ากลไกนี้เก็บนานแค่ไหน

**ตัว B หลังรวม**: **ลบถาวร กู้คืนไม่ได้** เหมือนกฎเดิม (ไม่เข้าถังขยะ) — เนื้อหาของ B ที่ไม่ได้เก็บหายไปเลย

**Dialog ยืนยัน (กู้คืนไม่ได้)** ต้องโชว์ครบ 5 อย่าง: (1) ชื่อ A และ B พร้อม Note แม่ของแต่ละอัน (2) สิ่งที่จะเกิด: จำนวนลูกของ B ที่ย้ายมา, Category ที่ย้ายมา, จำนวนไฟล์แนบที่ย้าย, ความยาวเนื้อหา A และ B (3) ตัวเลือกเรื่องเนื้อหา 4 แบบ (ตัวเลือกตั้งต้น = **ต่อ B ท้าย A** เพราะไม่มีข้อมูลหาย) (4) คำเตือนว่าลบ B ถาวรกู้คืนไม่ได้ และอันที่ถูกทิ้งเนื้อหาจะหายไปด้วย (5) **ตัวอย่างผลลัพธ์ทั้งหมด (preview เนื้อหาหลังรวม)** — คำตอบของเจ้าของโปรเจกต์ ต่างจากที่ผู้บันทึกแนะนำ; preview ต้องเปลี่ยนตามตัวเลือกเนื้อหาที่เลือกทั้ง 4 แบบ

**เงื่อนไขการเสนอรวม**
- ชื่อซ้ำเป๊ะใต้แม่เดียวกัน: ยังให้ **AI ตัดสิน** ว่าจะเสนอรวมหรือไม่ตามเกณฑ์เดิม (confidence สูง) ไม่เสนออัตโนมัติ (ซ้ำเป๊ะแสดงเฉพาะคำเตือนชื่อซ้ำตาม ticket 053)
- Note ในถังขยะ **ไม่นับ** เป็นตัวเลือกให้รวม
- **A เป็นลูกหลานของ B** → ไม่เสนอ (กันวนลูป); A เป็นแม่/บรรพบุรุษของ B รวมได้ตามปกติ

**ไม่ได้ตัดสิน (ขั้นออกแบบ)**: กลไกเปลี่ยนเส้นทางของการ์ดลิงก์ (ดูข้างบน), การตรวจเนื้อหาไม่เปลี่ยนก่อนยืนยัน (มี ticket 056 รองรับแล้ว), ขนาดเนื้อหารวมที่มากเกินกำหนด (ยังไม่มีเพดานขนาด Note), วิธีเก็บ event/read model ของ Search ตอน B ถูกลบ

**ผลต่อเอกสาร (ขั้นเอกสารปิดท้าย ยังไม่แก้ไฟล์)**: CONTEXT.md หัวข้อ **Topic Suggestion → Merge** (ชื่อใหม่ยังไม่ตั้ง) เขียนใหม่ทั้งหมดตามกฎนี้ (เดิมระบุ "Note ทั้งหมดใต้ Topic ใหม่ย้ายไปใต้ Topic เดิม" และข้อห้ามเมื่อทั้งคู่มี Note ซึ่งเลิกแล้ว); ARCHITECTURE.md ขั้นตอน Topic Suggestion flow ข้อ 7 (cross-schema transaction เหลือน้อยลงเพราะรวมเป็นเจ้าของเดียว ตาม ticket 053)

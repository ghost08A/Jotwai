# ADR 0015: ไฟล์แนบเก็บที่ S3-compatible storage โดย API เป็นคนส่งไฟล์ทุกครั้ง

## สถานะ
ยอมรับแล้ว (ตัดสินใจใน wayfinder map-v2, ticket 059 — ยังไม่ได้ implement) ยกเลิก non-goal "ไม่มีการแนบไฟล์/รูปภาพ" ของ ARCHITECTURE.md เดิม

## บริบท
requirements v2 ต้องการแนบรูปและไฟล์ใน Note แบบ Notion ตัวเลือกที่ research เปรียบเทียบไว้: ดิสก์ของ API, PostgreSQL (`bytea`/Large Object), S3-compatible storage แท็ก `<img>` แนบ Authorization header ไม่ได้ จึงต้องมีวิธีตรวจสิทธิ์เมื่อแสดงรูป และการแชร์ลิงก์ (ADR-0018) กำหนดให้ปิด/หมดอายุลิงก์แล้ว ไฟล์ต้องเปิดไม่ได้ทันที ซึ่งชนกับลิงก์ชั่วคราว (presigned URL) ของ S3 ที่ออกไปแล้วใช้ได้จนหมดอายุ

## การตัดสินใจ
- เก็บตัวไบต์ที่ **S3-compatible storage** (ยังไม่เลือกผู้ให้บริการ)
- **API ดึงไฟล์จาก storage แล้วส่งต่อให้ผู้ใช้/ผู้รับลิงก์แชร์ทุกครั้ง** ตรวจสิทธิ์ทุกครั้ง ไม่แจก presigned URL ให้เบราว์เซอร์
- **ข้อมูลของไฟล์** (ชื่อ ขนาด ชนิด Note ที่สังกัด key) อยู่ใน **Module Notes**; ไฟล์เป็นของ Note ใด Note หนึ่ง คัดลอกบล็อกรูปข้าม Note → ระบบคัดลอกไฟล์ให้ปลายทางได้ key ใหม่
- อ้างในเนื้อหา Markdown ด้วย `![ชื่อ](attachment:KEY)` (รูป) และ `[ชื่อ](attachment:KEY)` (ไฟล์) โดย KEY เป็นรหัสสุ่มยาว
- รับเฉพาะ allowlist (รูป png/jpg/gif/webp; pdf, txt, md, csv, docx/xlsx/pptx); ไม่รับ svg/html/exe/สคริปต์; ไฟล์ที่ไม่ใช่รูปเป็นดาวน์โหลดเท่านั้น; **ไม่สแกนไวรัสใน v2**
- เพดาน 10 MB ต่อไฟล์, ไม่จำกัดจำนวนต่อ Note, 500 MB ต่อผู้ใช้ (สำเนาจากการคัดลอกข้าม Note นับรวม)
- ไฟล์ที่ไม่ถูกอ้างถึงเกิน 7 วันถูกเก็บกวาด; Note ในถังขยะคงไฟล์ไว้; **ไม่เพิ่มการลบ Note ถาวรใน v2** (ไฟล์ของ Note ที่ลบแล้วกินพื้นที่ต่อไป)

## ผลที่ตามมา
- ไบต์ของทุกไฟล์ผ่านเซิร์ฟเวอร์ API (ภาระ/แบนด์วิดท์สูงกว่าแจกลิงก์ตรง) ยอมรับด้วยเพดาน 10 MB; ถ้าภายหลังหนักเกินไป การเปลี่ยนเป็นลิงก์ชั่วคราวอายุสั้นต้องตัดสินใหม่เพราะจะทำให้ "ปิดแล้วเปิดไม่ได้ทันที" มีช่องว่างเวลา
- ต้องมีบัญชี/credentials ของ storage และตัวจำลอง S3 สำหรับ dev (docker-compose); Content Polish ต้องไม่แตะอ้างอิง `attachment:KEY`
- การเลือกผู้ให้บริการ S3, ตาราง/รูปแบบ key ที่แน่นอน, การจัดการไฟล์กำพร้าตอนอัปโหลดแล้วไม่ได้บันทึก เป็นขั้นออกแบบ
